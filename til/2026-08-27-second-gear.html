Pre-read: Large code migrations usually fail as portfolio management problems before they fail as syntax problems: they touch many owners, sit below feature work, and require proof that behavior survived the rewrite. The new primitive is a verified batch system for code, where agents generate candidate diffs while tests, linters, sampling, and engineer review decide what can merge. This article is worth opening because it shows the operating model behind that shift.

Summary: Gergely Orosz uses Asana's Enzyme removal to argue that AI is turning years-long cleanup work into bounded engineering programs. OpenAI's Asana case study says Codex helped remove Enzyme in about two calendar weeks for roughly $12,000, against Asana's roughly $6 million staffing estimate. The important correction is that the five-year figure was not four engineers locked on one project for five years; it was the realistic completion horizon for low-priority opportunistic migration work.

The pattern matches earlier engineering writeups. Airbnb migrated nearly 3.5K React component test files from Enzyme to React Testing Library in six weeks by using validation steps, retries, rich context, and breadth-first tuning. Uber's JUnit migration shows the same shape at larger scale: automated transformation plus repeated validation, with engineers designing the loop and handling hard cases. The durable point is that AI does not make migration judgment disappear. It changes migration from scattered manual toil into an auditable factory for long-deferred codebase change.

Happenings Background jobs become agent infrastructure

Pre-read: Long-running AI work has the same systems pressure as ordinary background work: it must leave the request path, survive retries, expose state, and avoid duplicating side effects. Queues and schedulers become product infrastructure once agents run tasks that last minutes or hours.

Summary: ByteByteGo walks through why teams move slow, bursty, or failure-prone operations out of synchronous user requests. A profile-photo upload is the concrete example: store the object first, then resize it, scan it, push variants to a CDN, and update metadata asynchronously. The piece groups background work by trigger: user actions, clocks, external systems, and volume thresholds. Its useful frame is evolutionary. Teams can start with one scheduled script, but complexity pushes them toward job queues, retries, idempotency, and distributed orchestration. For agentic software, that same progression is likely to show up in product surfaces rather than only backend plumbing.

Ideation

Ideation

Idea 1 Change Escrow for Agentic Migrations

Sell VP Engineering and platform teams a verification layer for large AI-run migrations: every agent change goes into an evidence escrow with the intended behavior, generated tests, replay logs, semantic diffs, rollback plan, and a signoff packet a human can actually trust. The company is not another coding agent. It is the transaction system for letting agents make thousands of background changes without turning production code into an unreviewable pile of almost-right edits.

Why Now

Frontier coding agents are good enough to make old migrations economically rational, but the bottleneck has moved to trust. Enterprises can tolerate a human changing 40 files with normal review. They cannot tolerate an agent changing 40,000 files unless someone can prove what changed, what did not change, and how to unwind the run.

First Wedge

Start with one migration class that has obvious demand and objective validation: test-framework, API-version, or dependency migrations in large TypeScript and Java monorepos. The first product ingests the repo, migration goal, test commands, coverage history, and CI logs, then produces a migration runbook plus an evidence packet for each merged batch.

Commercial Model

Sell to platform engineering, developer productivity, and infrastructure teams as a per-migration project fee plus seat-based usage for ongoing evidence storage. A credible first price is $25K-$100K for a migration workstream, because the avoided cost is measured in engineer-months and the budget already lives in developer productivity or technical-debt programs.

Defensibility

The compounding asset is not prompts; it is a private corpus of migration invariants, failure modes, semantic diff patterns, flaky-test signatures, and reviewer decisions across real enterprise codebases. Incumbent coding agents can generate patches, but they do not naturally become the neutral audit trail, rollback registry, and risk record that legal, security, and engineering leadership can all accept.

Technical Risk

The hard part is proving semantic preservation when tests are incomplete. The system needs static analysis, dynamic traces, coverage-gap detection, mutation testing, and targeted human review routing without pretending it can mathematically prove every application behavior.

Market Expansion

After code migrations, the same primitive expands to Salesforce workflow rewrites, data-pipeline migrations, IAM-policy refactors, ERP configuration changes, and regulated documentation updates. The common shape is high-volume background change where agents can do the work but buyers need evidence before they trust the result.

Self-Critique

This can fail if buyers decide ordinary CI plus senior review is enough, or if coding-agent vendors bundle lightweight migration dashboards before the category is named. The wedge has to be serious risk reduction for painful migrations, not a pretty report on top of GitHub pull requests.

Next Experiment

In two weeks, take three public migration PR sets or partner with one engineering team sitting on a legacy migration. Build a thin CLI that produces semantic diff summaries, coverage-gap maps, generated regression tests, and reviewer packets. The validation question is simple: would the team merge a larger batch with this evidence than they would without it?
